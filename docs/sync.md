# Sync protocol — `note-haven` REST JSON API

The app's Settings page (gear icon in the header) connects to a sync server to
keep notes replicated across devices. This document specifies the wire protocol
so anyone can implement a compatible server in an afternoon.

## Design goals

- **Local-first.** IndexedDB is always the source of truth for the UI. Sync is
  an explicit merge step; the app works fully offline.
- **Dead simple.** Four endpoints, plain JSON, no per-client state on the
  server beyond the notes themselves.
- **Privacy-preserving.** Encrypted notes sync only in their encrypted form
  (`content` is the `"[encrypted]"` placeholder and the `encrypted` payload
  travels verbatim). Plaintext for encrypted notes never leaves the device.
- **Last-writer-wins per note**, with deletions propagated via tombstones on
  both sides. Newer `updatedAt` wins; equal timestamps are no-ops.

## Endpoint contract

Base path: the server URL configured in Settings, e.g. `https://sync.example.com`.

| Method | Path                  | Request body        | Response                              |
|--------|-----------------------|---------------------|---------------------------------------|
| GET    | `/api/notes`          | —                   | `200` `{ "notes": [RemoteMeta, ...] }` |
| GET    | `/api/notes/{uid}`    | —                   | `200` full note payload (or `404`)     |
| PUT    | `/api/notes/{uid}`    | full note payload   | `200` or `204` (upsert)                |
| DELETE | `/api/notes/{uid}`    | —                   | `200` or `204` (idempotent)            |

Notes:

- `{uid}` is an opaque ASCII identifier (currently a UUID) generated by the
  client. Servers must treat it as an opaque string key and MUST percent-decode
  it.
- `RemoteMeta` is `{ "uid": string, "updatedAt": ISO-8601, "deleted": true? }`
  — the manifest lists every known uid including deleted ones (tombstones) so
  clients can propagate deletions. Servers may omit `deleted` when false.
- `updatedAt` comparisons are ISO-8601 timestamps; malformed entries in the
  manifest are ignored by the client.
- A `GET /api/notes/{uid}` for a tombstoned uid SHOULD return `404`; clients
  that still hold the note treat a `deleted: true` manifest entry as the
  authority and won't fetch it.

### CORS

The app is browser-hosted and cross-origin from the server, so servers MUST
implement CORS:

- `OPTIONS` preflight → `204` with
  `Access-Control-Allow-Methods: GET, PUT, DELETE, OPTIONS` and
  `Access-Control-Allow-Headers: Authorization, Content-Type`.
- Actual responses → `Access-Control-Allow-Origin` for the app origin
  (`*` for a private deployment is fine).

## Authentication

Optional. If configured, the client sends every request:

```
Authorization: Bearer <token>
```

Servers SHOULD return `401`/`403` on missing/invalid tokens. Requests are
otherwise unauthenticated; TLS termination is the deployment's responsibility.

## Note payload (the wire shape of one note)

```jsonc
{
  "uid": "0b7f…",                  // mirrors the path uid
  "title": "Trip planning",
  "content": "# Trip planning\n\n…markdown…",   // or "[encrypted]"
  "tags": ["travel"],
  "category": "General",
  "attachments": [ /* { id, name, type, data (data: URL or external URL), size, thumbnail? } */ ],
  "createdAt": "2026-09-20T01:00:00.000Z",
  "updatedAt": "2026-09-20T02:00:00.000Z",      // THE conflict-resolution clock
  "editDates": ["2026-09-20"],
  "pinned": false,
  "hasCodeBlocks": true, "hasMermaid": false,   // renderer fast-flags (optional)
  "hasGeoJson": false, "hasModel3D": false,
  "encrypted": null              // or { method, ciphertext, iv, salt?/wrappedKey?, mac?, keyFingerprint? }
}
```

Servers SHOULD store payloads opaquely (blob + indexed fields) and MUST NOT
require unknown fields to survive — newer clients may add fields.

## Merge semantics (client-side, for reference implementations)

1. Client fetches the manifest and compares per-uid `updatedAt` against local
   notes (uids are mapped locally to note ids).
2. Per uid:
   - local newer → `PUT` the local note (push);
   - remote newer → `GET` and overwrite local (pull);
   - equal → nothing.
3. Deletions:
   - local note deleted since the last sync → client `DELETE`s the remote note;
   - remote manifest `deleted: true` → client deletes its local copy, UNLESS
     the local copy was edited after the remote deletion (then it pushes and
     resurrects).
   - a tombstoned uid whose note was edited on the server after the deletion is
     pulled back (the edit wins).
4. `PUT`/`DELETE` failures are collected and retried next sync; one failing
   note never blocks the others.

## Reference server (minimal Express sketch)

```js
import express from 'express';
const app = express();
app.use(express.json({ limit: '50mb' }));
app.use((req, res, next) => {
  res.set({
    'Access-Control-Allow-Origin': '*',
    'Access-Control-Allow-Methods': 'GET, PUT, DELETE, OPTIONS',
    'Access-Control-Allow-Headers': 'Authorization, Content-Type',
  });
  if (req.method === 'OPTIONS') return res.sendStatus(204);
  // TODO: verify req.get('Authorization') === 'Bearer <your token>'
  next();
});

// notes: Map<uid, payload> — persist however you like
app.get('/api/notes', (req, res) =>
  res.json({ notes: [...notes.values()].map(n => ({ uid: n.uid, updatedAt: n.updatedAt })) }));
app.get('/api/notes/:uid', (req, res) => {
  const n = notes.get(req.params.uid);
  n ? res.json(n) : res.sendStatus(404);
});
app.put('/api/notes/:uid', (req, res) => { notes.set(req.params.uid, req.body); res.sendStatus(204); });
app.delete('/api/notes/:uid', (req, res) => { notes.delete(req.params.uid); res.sendStatus(204); });

app.listen(8787);
```

## Storage layout on the client

- Settings (server URL, token, auto-sync cadence) live in
  `localStorage` under `notehaven.sync.settings`.
- Deletion tombstones (90-day TTL, capped at 500) live under
  `notehaven.sync.tombstones`.
- The note-id → uid mapping lives under `notehaven.sync.uidMap`.
  Nothing about sync touches the IndexedDB schema.
